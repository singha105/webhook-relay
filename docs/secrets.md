# Secrets in a GitOps repository

> "How do you do GitOps without putting secrets in Git?"

You do put them in Git. You put them in *encrypted*, and you keep the
decryption key out.

This repository uses two mechanisms, because they solve different halves of the
problem.

---

## The constraint

GitOps means the repository is the desired state. If a secret is not in the
repository, something outside the repository has to inject it — and now the
cluster's actual state depends on a step nobody can see, review, or reproduce.
That is the failure mode: `kubectl create secret` run once by a person who has
since left.

But a plaintext secret in Git is worse. Git has no forgetting: a secret pushed
once is in the history of every clone, forever, and rotating it does not remove
it.

So: encrypted in Git, key held elsewhere.

---

## Sealed Secrets — for anything ArgoCD deploys

**How it works.** The controller generates an RSA keypair on first start. You
encrypt with the public half using `kubeseal`, producing a `SealedSecret`
custom resource. That resource is committed. ArgoCD applies it like any other
manifest, and the controller decrypts it in-cluster into a normal `Secret`.

**Why it is the default here.** A `SealedSecret` is just a manifest. ArgoCD
needs no plugin, no sidecar, and no key of its own. Nothing about the delivery
pipeline changes to accommodate it.

**Sealing a secret:**

```bash
kubectl create secret generic webhook-relay-signing \
  --namespace webhook-relay \
  --from-literal=key="$(openssl rand -base64 32)" \
  --dry-run=client -o yaml \
| kubeseal --controller-name sealed-secrets-controller \
           --controller-namespace kube-system \
           --format yaml \
> gitops/secrets/signing-sealed.yaml

git add gitops/secrets/signing-sealed.yaml && git commit
```

The plaintext never touches disk — it is piped straight into `kubeseal`.

**Scope.** By default a SealedSecret can only be decrypted into the *same
namespace and name* it was sealed for. That is a feature: someone who can read
the repository cannot move the ciphertext into a namespace they control and
have the controller decrypt it for them.

### The thing people get wrong

**The private key lives in the cluster.** Recreate the cluster and every
committed `SealedSecret` becomes undecryptable, because the new controller
generated a new key. The symptom is confusing — ArgoCD syncs green, the
`SealedSecret` exists, and no `Secret` ever appears.

Back the key up:

```bash
make seal-backup    # writes sealed-secrets-key.yaml, gitignored
```

Restore it into a rebuilt cluster *before* ArgoCD syncs:

```bash
kubectl apply -f sealed-secrets-key.yaml
kubectl delete pod -n kube-system -l name=sealed-secrets-controller
```

`sealed-secrets-key.yaml` contains the private key in plaintext. It is
gitignored, and in a real deployment it belongs in a password manager or an
offline KMS — not on a laptop.

## SOPS + age — for values a human or CI needs

A `SealedSecret` can only ever be decrypted by the controller. That is exactly
wrong for a value you need in a Terraform variable, a local `.env`, or a CI job.

SOPS encrypts the *values* of a YAML file and leaves the keys readable, so a
diff still shows which secret changed without revealing what it changed to.

```bash
age-keygen -o age.key                     # gitignored; back this up
export SOPS_AGE_KEY_FILE=age.key
sops --encrypt --age "$(grep -o 'age1.*' age.key)" \
     --encrypted-regex '^(password|token|key|secret)$' \
     secrets.dec.yaml > secrets.enc.yaml   # this one is committed
```

`.sops.yaml` in the repository root pins the recipient so `sops -e` needs no
flags.

### Why not SOPS for the ArgoCD path

To use SOPS-encrypted manifests with ArgoCD you need a config-management plugin
(`ksops`, `argocd-vault-plugin`). That means a sidecar on the repo-server, the
age private key mounted into it, and a second component that can fail between a
commit and a deployment. Sealed Secrets needs none of that.

## What is actually secret in this project

| Value | Mechanism | Why |
|---|---|---|
| Postgres app password | Generated by Terraform, written to a `Secret` | Never in Git at all — the strongest option, available because Terraform creates the cluster |
| Grafana admin password | Generated by Terraform | Same |
| Endpoint signing secrets | Generated per endpoint at runtime, stored in Postgres | Application data, not configuration |
| Registry pull credentials | Not needed | GHCR packages are public |

So the honest answer for *this* system is that very little needs sealing — the
generated-at-provision-time pattern is better than encrypting-and-committing
wherever it is available. Sealed Secrets is set up because a real deployment
always grows a secret that cannot be generated (a third-party API key), and
because the question is worth being able to answer concretely.

---

## What none of this protects against

- **A compromised cluster.** The decryption key is in it.
- **Ciphertext is forever.** Rotating a secret does not remove the old
  ciphertext from Git history. Rotation means changing the *underlying* secret,
  not just re-sealing it.
- **Key rotation is manual.** Sealed Secrets rotates its key every 30 days by
  default but keeps old keys to decrypt existing resources; nothing re-seals
  old ciphertext with the new key. A real deployment needs a job for that.
